# Deadline และการยกเลิก
> บอกล่วงหน้าว่ารอได้นานแค่ไหน พอหมดเวลาทั้ง client และ server ก็เลิกทำพร้อมกัน

ถ้าไม่ตั้ง deadline การเรียกที่ค้างจะรอไปเรื่อย ๆ thread หรือ connection ก็ถูกจองไว้ไม่ปล่อย พอเจอ server ตัวหนึ่งอืด ความอืดก็ลามไปทั้งระบบ ทีม gRPC เลยแนะนำตรง ๆ ว่า **ทุก call ควรมี deadline**

deadline ของ gRPC มีสองอย่างที่ต่างจาก timeout ทั่วไป

- **server รู้ด้วย** ค่า deadline ถูกส่งไปใน header `grpc-timeout` server เลยรู้ว่ายังเหลือเวลาอีกเท่าไร
- **ส่งต่อเป็นทอด ๆ ได้** ถ้า server ต้องไปเรียก service อื่นอีก ก็ส่ง context เดิมต่อไปได้เลย เวลาที่เหลือจะลดลงไปเรื่อย ๆ ตามสาย ไม่มีใครรอนานเกินกว่าที่ต้นทางรอไหว

ลองปรับ deadline ให้น้อยกว่าเวลาที่ server ใช้ แล้วดูว่าเกิดอะไรขึ้น จากนั้นสลับไปสถานการณ์ "ผู้ใช้กดยกเลิก"

===notes===

## สองกรณีนี้ต่างกันยังไง

| | `DEADLINE_EXCEEDED` (4) | `CANCELLED` (1) |
|---|---|---|
| เกิดจาก | เวลาหมด | client สั่งยกเลิกเอง |
| ตัวอย่าง | API ปลายทางช้าเกิน 2 วินาที | ผู้ใช้ปิดหน้าจอ หรือกดปุ่มยกเลิก |
| ควร retry ไหม | อาจจะ ถ้า method นั้นเรียกซ้ำได้อย่างปลอดภัย | ไม่ต้อง เพราะไม่มีใครอยากได้ผลแล้ว |

## สิ่งที่ควรจำ

- ฝั่ง client ตั้ง deadline จากมุมของผู้ใช้ ถามตัวเองว่า "ผู้ใช้รอหน้าจอนี้ได้นานแค่ไหน"
- ฝั่ง server ต้องส่ง context หรือ cancellation token ต่อให้ database, HTTP client และ gRPC call ตัวถัดไปเสมอ ไม่อย่างนั้น client เลิกรอไปแล้ว แต่ server ยังทำงานทิ้งอยู่
- อย่าตั้ง deadline แบบตายตัวในทุกชั้นของระบบ ถ้าชั้นนอกให้ 1 วินาที ชั้นในตั้ง 5 วินาทีก็ไม่มีประโยชน์ ใช้เวลาที่เหลือจาก context แทน
- stream ที่ตั้งใจเปิดค้างนาน ๆ ไม่ต้องตั้ง deadline สั้น ให้ใช้การยกเลิกกับ keepalive ดูแลแทน
