# ความปลอดภัย: TLS และ mTLS
> เข้ารหัสทุก frame และพิสูจน์ว่าแต่ละฝั่งเป็นตัวจริง ไม่ใช่ใครก็ไม่รู้ที่ดักอยู่กลางทาง

ตัวอย่างในบทก่อน ๆ ใช้ `insecure` เพื่อให้อ่านง่าย แต่ถ้าเป็นของจริง ทุก connection ควรวิ่งผ่าน TLS ข้อมูล order, token และข้อมูลลูกค้าจะได้ไม่ถูกอ่านระหว่างทาง

**TLS ปกติ** ให้ client ตรวจใบรับรองของ server แบบเดียวกับที่เบราว์เซอร์ตรวจตอนเปิดเว็บ https client จะรู้ว่ากำลังคุยกับ `orders.internal` ตัวจริง แต่ฝั่ง server ไม่รู้ว่าใครเรียกมา ต้องไปพึ่ง token ใน metadata อีกที

**mTLS (mutual TLS)** ให้ตรวจทั้งสองทาง client ก็มีใบรับรองของตัวเองเหมือนกัน server เลยรู้ตั้งแต่ระดับ connection ว่าคนที่เรียกคือ `checkout-service` วิธีนี้นิยมใช้ให้ service ภายในยืนยันตัวตนกัน

ลองสลับสองโหมดแล้วดูว่า handshake ต่างกันตรงไหน

===notes===

## สิ่งที่ควรจำ

- gRPC บังคับให้ตกลงใช้ HTTP/2 ผ่าน ALPN ตอน handshake proxy หรือ load balancer ที่ไม่รองรับ ALPN จะทำให้ต่อไม่ติด
- TLS กับ token ใช้ร่วมกันได้ และควรใช้ร่วมกันด้วย TLS ปกป้องช่องทาง ส่วน token (เช่น JWT ใน `authorization`) บอกว่าผู้ใช้คนไหนเป็นคนสั่ง
- ทำ mTLS เองต้องดูแลใบรับรองหลายร้อยใบ ทั้งออกใหม่และหมุนเวียนก่อนหมดอายุ หลายทีมเลยให้ service mesh อย่าง Istio หรือ Linkerd ทำ mTLS ให้อัตโนมัติ แล้วตัวโค้ดคุยกันแบบ plaintext ภายใน pod
- ใน .NET การตั้งค่า TLS ส่วนใหญ่อยู่ที่ Kestrel ไม่ได้อยู่ในโค้ด gRPC
- อย่าปิดการตรวจใบรับรอง (`InsecureSkipVerify` หรือเทียบเท่า) บน production เด็ดขาด ถึงจะยังเข้ารหัสอยู่ แต่ใครจะปลอมตัวเป็น server ก็ทำได้
