# Client streaming
> client ทยอยส่งข้อมูลไปหลายก้อน แล้ว server ตอบกลับครั้งเดียวตอนจบ

รูปแบบนี้กลับด้านกับบทก่อน คราวนี้ client เป็นฝ่ายส่งหลายครั้ง ส่วน server รอจนได้ข้อมูลครบแล้วค่อยตอบกลับก้อนเดียว ใน `.proto` ย้ายคำว่า `stream` มาไว้ฝั่ง request

```proto
rpc UploadItems(stream Item) returns (UploadSummary);
```

ในตัวอย่างนี้ client ส่งสินค้าในตะกร้าทีละชิ้น ถ้าใช้ REST คุณต้องรวบทุกชิ้นใส่ JSON ก้อนใหญ่ก้อนเดียว หรือไม่ก็ยิง request แยกทีละชิ้น แบบแรกกิน memory ถ้าข้อมูลเยอะ ส่วนแบบหลังเสีย round-trip ทุกครั้ง client streaming ได้ข้อดีของทั้งสองแบบ ส่งทีละชิ้นบน connection เดียว แล้ว server ก็นับไปพร้อมกันได้เลย

สังเกต frame สุดท้ายของ client ในแผนภาพ เป็น DATA ว่างที่มี flag `END_STREAM` เป็นสัญญาณบอก server ว่า "ส่งครบแล้ว" ถึงตอนนั้น server ถึงจะตอบกลับ

===notes===

## สิ่งที่ควรจำ

- การปิดฝั่งส่งเรียกว่า **half-close** client ยังรอฟังคำตอบได้อยู่ แค่ไม่ส่งอะไรเพิ่ม
- ถ้า client ลืม half-close server จะรอไปเรื่อย ๆ จนกว่า deadline จะหมด เป็น bug ที่เจอบ่อยมาก
- แต่ละภาษาใช้คำสั่งต่างกัน Go ใช้ `CloseAndRecv()` Node.js ใช้ `call.end()` C# ใช้ `CompleteAsync()` ส่วน Python แค่ให้ generator ทำงานจบ
- server ตอบ error กลางทางได้ตลอด ไม่ต้องรอ client ส่งครบ เช่นเจอสินค้าที่ไม่มีในระบบก็ตอบ `INVALID_ARGUMENT` ทันที
- งานที่เหมาะ เช่น อัปโหลดไฟล์เป็นชิ้น ๆ, ส่งค่าจาก sensor เป็นชุด, นำเข้าข้อมูลหลายพันแถว
